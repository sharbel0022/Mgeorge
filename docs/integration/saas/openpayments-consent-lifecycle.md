# Joined company consent lifecycle

PR #39 joins the authoritative foundation and the Open Payments provider without replacing the existing Enable Banking workspace. D1 migration `0020_bank_consent_context` follows foundation `0019_company_boundaries`, preserves the original four additive consent fields and adds `saas_bank_state` with all owner boundary triggers. Its snapshot includes both migrations. Node adds the equivalent table and preserves company-partition routing.

`sites/lib/banking/openpayments-lifecycle.js` is the common application lifecycle, using the actual `OpenPaymentsProvider` operations. `saas-bank-runtime.js` supplies the public snapshot, durable request idempotency and sync facade. Sites `saas-runtime.ts` and Node `src/saas-bank-runtime.js` provide guarded database storage. All provider handles and callback state are encrypted at rest, bound to owner and purpose. No financial ledger is added.

The redirect state originates in the documented Open Payments authorization template. Callback compares state, initiating actor/company/context versions and browser-session binding, atomically consumes pending state, activates the provider code exactly once, checks live consent, and lists approved corporate account resources. Completed identical callbacks return their saved result; a different code/state or concurrent consumer cannot activate again. Account selection performs fresh consent and exact account-resource reads. Stored expiry is the minimum of requested validity and the provider-confirmed expiry returned with account discovery. No local success is inferred from the callback query alone.

The API's existing documented authorization-code adapter does not expose PKCE configuration. No fictitious PKCE or BankID flow is added. Redirect capability is checked using the provider. Decoupled-only banks produce unsupported status rather than a simulated approval. BankID person identification alone never establishes company authority.

New SaaS banking is disabled unless `SAAS_BANK_ENABLED` equals `true`. Configuration is JSON in `SAAS_OPENPAYMENTS_CONFIG`, validated by the existing provider. `SAAS_OPENPAYMENTS_REGISTRATIONS` is a trusted server-controlled array: each entry has companyId, actorId, corporateId, psuId, bicFi, bankId, bankName, psu request evidence and explicit `verified`, `corporateAccessVerified`, `redirectVerified` booleans. Optional authenticationMethodId selects a provider-returned method; ambiguous methods require configuration. Bankgiro is offered only with `bankgiroVerified:true` and provider configuration supporting it. Server configuration is pinned and rechecked across asynchronous operations.

Production additionally requires a verified mTLS transport. The Sites facade currently has no configured mTLS transport, so production capability remains unavailable. This is an external activation boundary, not a claim of production readiness. All examples/tests use synthetic data and injected transport; no bank, Gmail, customer or financial production write occurs.

Mutations require a bounded Idempotency-Key plus expectedRevision. Durable CAS prevents parallel starts, stale account changes and concurrent disconnection races. A lost start response can recover the same authorization. Failed remote revocation remains `revocation_pending`, clears selected accounts immediately and can retry with the same request key. Renewal first revokes the previous grant, so there is a deliberate interval without usable bank access until the new grant completes. A failed/ambiguous activation cannot be reused; disconnect/restart is required.

The sync facade reads local state only and returns `{context,provider,account,assertCurrent,verifyConsent}`. `context.consentId` is a SHA-256 descriptor, never a token. The caller must execute `verifyConsent` and `provider.getTransactions(account.handle, input)` through the existing job's request/quota accounting and call assertCurrent at the final write boundary. A trusted verified ratePolicy is mandatory; no quota is guessed. Node financial transactions additionally use the synchronous exact revision/payload and current company fence. There is no additional scheduler.

Banking state is included in the encrypted backup census. Historical 20-table and 22-table snapshots remain valid without invented rows; new backups include the new durable state. Evidence restore remains isolated and does not activate a membership or source.

Focused verification includes the actual provider synthetic redirect journey, wrong actor/session/company, read-only/accountant denial, invalid account IDs, replay, concurrent revision checks, membership revocation during a provider await, expiry, durable request retries, inactive capability and the local-only sync handoff. Full gate results are recorded in the integration owner's report after completion.
